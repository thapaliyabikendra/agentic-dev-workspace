# Test Data Generation Rules

> **Type:** Workflow reference. Consulted at Phase 2 (Test plan ingest) and
> Phase 3 (Test suite codegen). See
> [`plan.md → Test plan ingest`](plan.md#6-fs-validation-loop)
> for how Test Data entries are emitted into each TC's `## Test Data`
> section, and
> [`test-suite-codegen.md`](test-suite-codegen.md)
> for how those entries are interpolated into test runner code.
> Codifies the four placeholder tokens (`{timestamp}`, `{counter}`,
> `{uuid}`, `{tcNumber}`), the directive vocabulary for matrix-driven
> TCs (`violatesMaxLength`, `duplicate`, `invalidFormat`, etc.), and
> per-field-type × TC-intent generation rules.

## When to Use

**Use when:** Phase 2 test-plan ingest is populating the `## Test
Data` section of a freshly emitted TC, Phase 3 codegen is
interpolating concrete values into a test spec file, or a TC
self-check is validating that unique fields carry `{timestamp}` /
`{uuid}` per the happy-path uniqueness rule.

**Do NOT use when:** the work is identifying which TCs should exist
at all (use [`coverage-matrix.md`](coverage-matrix.md) — completeness
check, not values), mapping a TC step to runner code (use
[`test-runner-cookbook.md`](test-runner-cookbook.md) — code emission,
not value generation), or the artifact is not a TC under an FS's
`test-plans/<use-case>/` folder (this file applies only to the Test
Data section of TC files).

**Vs. sibling files:** [`coverage-matrix.md`](coverage-matrix.md)
identifies *which* TCs to emit; this file generates *the values*
inside each emitted TC. [`test-runner-cookbook.md`](test-runner-cookbook.md)
generates *the code* that consumes those values. The three are the
**TC authoring trio** at Phase 2 / Phase 3.

Used at Phase 2 to populate the `## Test Data` section of every TC, and at
Phase 3 to interpolate concrete values into test spec files.
This file is the recipe that turns a field's constraints (from the
data-model fact sheet, sourced from scoped `nodes/entities/ENT-NNN-*.md`
files in the active FS) plus the TC's intent (happy-path /
required-missing / max-length / duplicate / authorization / etc.) into a
Test Data entry.

This file does not generate values for itself. Phase 2 walks the rules
below per field, per TC; the values land in each TC's `## Test Data`
section. Phase 3 reads those entries and substitutes runtime values
into the generated test spec.

## Templated value vocabulary

Four placeholder tokens cross the Phase 2 → Phase 3 boundary. Phase 2
emits them literally in the TC file; Phase 3 (test suite codegen)
interpolates them into the generated test code at code-generation
time.

| Token | Replaced at codegen with | Use when |
|---|---|---|
| `{timestamp}` | `Date.now()` (epoch ms) | Need a value unique per test run |
| `{counter}` | An incrementing per-spec-file counter | Need a value unique per test within a single spec |
| `{uuid}` | A generated UUID | Need a guaranteed-unique value, length doesn't matter |
| `{tcNumber}` | The TC's own number (e.g. `TC001`) | Need a value identifiable to a specific TC |

**Combination is allowed and encouraged.** `TC{tcNumber}-RT-{timestamp}`
produces something like `TC001-RT-1746604800000` at runtime — short,
unique, traceable back to the TC. This is the workhorse pattern for
happy-path string fields on unique columns.

**Order of preference:**

1. `{tcNumber}` + `{timestamp}` — most common; identifies the TC, guarantees uniqueness.
2. `{tcNumber}` alone — when timestamp uniqueness isn't needed (e.g. local fixtures cleaned between runs).
3. `{uuid}` — only when length doesn't matter and human-readability isn't valued.
4. Pure literal — for FRS-stated values like `Category: "Option A"`.

Avoid `{counter}` unless within-spec uniqueness is genuinely needed —
`{timestamp}` is sufficient for cross-test isolation.

## Directive vocabulary (matrix-driven TCs)

For TCs generated by the Required Coverage Matrix (max-length, duplicate,
required-missing, etc.), the Test Data entry uses a
`human description → directive(args)` form. The description is for the
human reviewer; the directive is what Phase 3 codegen consumes to
validate or generate the value.

| Directive | Args | Meaning |
|---|---|---|
| `violatesMaxLength(N)` | max length in chars | Generate a string exactly `N+1` characters long |
| `violatesMinLength(N)` | min length | Generate a string of length `N-1` (or empty if N=1) |
| `duplicate(value)` | the value to duplicate | Reference Pre-existing State — this value MUST already exist in DB |
| `invalidFormat(kind)` | `email \| url \| date \| phone \| number \| decimal` | Generate a value that violates the named format |
| `outOfRange(min, max)` | numeric bounds | Generate a number outside `[min, max]` (below min if min>0, above max otherwise) |
| `whitespaceOnly` | (none) | Generate `"   "` (3 spaces) |
| `empty` | (none) | Empty string `""` |
| `null` | (none) | Literal null (skip the fill step entirely; not the same as empty) |
| `injection` | `sql \| xss \| script` | Generate a known injection payload for the kind |

**Always emit BOTH the human description AND the directive.** Example:

```
Template Name: 51-character string → violatesMaxLength(50)
Code: existing value 'TC-DUP-001' → duplicate('TC-DUP-001')
Email: 'not-an-email' → invalidFormat(email)
```

## Generation rules per field type × TC intent

### String fields (text, textarea, varchar)

Constraints captured in the data-model fact sheet: required, max length,
min length, uniqueness, format (regex), whitespace-trimmed, etc. Source
is the scoped `nodes/entities/ENT-NNN-*.md` file's `Invariants`,
`Properties`, and `Constraints` sections, plus any field-level
clarifications in the FRS's `## Acceptance criteria` or the
Phase-1-born FLW's Scenarios.

| TC intent | Test Data entry |
|---|---|
| Happy path (valid input) | `Field Name: TC{tcNumber}-{kebab-feature}-{timestamp}` if max length ≥ 30, else `TC{tcNumber}{counter}` |
| Required missing | `Field Name: (empty) → empty` |
| Max length exceeded | `Field Name: <(maxLength+1)-character string> → violatesMaxLength({maxLength})` |
| Min length violation | `Field Name: <(minLength-1)-character string> → violatesMinLength({minLength})` |
| Duplicate value | `Field Name: <existing value> → duplicate('<existing value>')` (also requires Pre-existing State entry) |
| Whitespace-only | `Field Name: '   ' → whitespaceOnly` |
| Format invalid | `Field Name: <a value violating the format> → invalidFormat({kind})` |
| Special chars / injection | `Field Name: <payload> → injection(xss)` (or `sql`, `script`) |

**Happy-path uniqueness rule.** When the field is unique, the templated
value MUST include a per-run uniqueness component — `{timestamp}` or
`{uuid}`. `{tcNumber}` alone won't do because re-runs collide. The
ingest exit criteria verify this: if a unique field's happy-path Test
Data entry doesn't include `{timestamp}` or `{uuid}`, the ingest blocks.

**Field-name normalisation.** The Test Data entry uses the field's
human-readable name as it appears in the FRS or scoped Entity node, NOT
the camelCase property name. `Template Code` not `templateCode`. Phase
3 codegen matches step text → Test Data entry by case-insensitive
substring, so step text *"Enter a value in the Template Code field"*
matches the entry *"Template Code: ..."*.

### Numeric fields (integer, decimal)

Constraints: required, min, max, decimal precision.

| TC intent | Test Data entry |
|---|---|
| Happy path | `Field Name: <a value within [min, max]>` (e.g. midpoint, or a sensible default like 100) |
| Required missing | `Field Name: (empty) → empty` |
| Out of range (below min) | `Field Name: <min - 1> → outOfRange({min}, {max})` |
| Out of range (above max) | `Field Name: <max + 1> → outOfRange({min}, {max})` |
| Negative when not allowed | `Field Name: -1 → outOfRange(0, {max})` |
| Decimal precision exceeded | `Field Name: <value with too many decimal places> → invalidFormat(decimal)` |

If the scoped Entity node and FRS don't declare a min/max, pick `100`
for happy-path integers, `100.00` for decimals — flag with a comment
for human review.

### Boolean / toggle / checkbox

Constraints: default value, required.

| TC intent | Test Data entry |
|---|---|
| Happy path (set true) | `Field Name: true` |
| Happy path (set false) | `Field Name: false` |
| Toggle on→off (matrix) | `Field Name: false  (precondition: was true)` |
| Toggle off→on (matrix) | `Field Name: true  (precondition: was false)` |

### Select / dropdown / ng-select

Constraints: option list (if enumerated by the Entity node or FRS),
required, multi-select.

| TC intent | Test Data entry |
|---|---|
| Happy path (option known) | `Field Name: '<option literal>'` |
| Happy path (option unknown) | `Field Name: (select first available option)` — flag for human review |
| Required missing | `Field Name: (no selection) → empty` |
| Invalid option (rare) | `Field Name: <invalid string> → invalidFormat(option)` |

When the Entity node or FRS enumerates options
(e.g. `Category: { Option A, Option B, Option C }`), pick the
first option as the happy-path value. When only the field type is
described, emit `(select first available option)` and let Phase 3
codegen emit a runtime "pick first option" pattern.

### Date / datetime

Constraints: required, min, max, format.

| TC intent | Test Data entry |
|---|---|
| Happy path (any date) | `Field Name: 2026-01-15` (a fixed sensible date — neither past-only nor future-only without guidance) |
| Happy path (must be future) | `Field Name: <today + 30 days, ISO 8601>` — emit `{futureDate(30)}` if codegen supports it; otherwise flag for human review |
| Past when must be future | `Field Name: 2020-01-01 → outOfRange(today, +infinity)` |
| Invalid format | `Field Name: 'not-a-date' → invalidFormat(date)` |

Date rules are the area most likely to need future extension; if the
project routinely has constraints like `must be ≥ today` or `must be
within 30 days`, extend the directive vocabulary with `{futureDate(N)}`
/ `{pastDate(N)}` tokens then.

### File upload

Constraints: required, file types, max size.

| TC intent | Test Data entry |
|---|---|
| Happy path | `Field Name: <fixture: validUpload-<feature>.<ext>>` — references a fixture file the team provides; flag for human review since binary fixtures can't be generated from prose |
| Required missing | `Field Name: (no file) → empty` |
| Wrong file type | `Field Name: <fixture: wrongType.<ext>> → invalidFormat(fileType)` |
| Oversized | `Field Name: <fixture: oversized.<ext>> → violatesMaxLength({maxBytes})` |

File uploads always reference a fixture file. Phase 2 emits the fixture
name; the `tests/` folder is responsible for providing the actual file.
This is one of the few places where prose alone isn't enough — codegen
needs a real file path.

## Sub-section presence

Inside `## Test Data`, two sub-sections may appear:

- `### Pre-existing State` — included only when the TC needs database
  state to exist before any step runs (matrix-driven duplicate, FK
  delete, edit-non-existent, restore-after-soft-delete, etc.). Omitted
  entirely otherwise.
- `### Form Input` — included only when the TC has at least one `fill`,
  `select`, or `toggle` step. Pure read/view TCs omit it entirely.

A TC with neither omits the whole `## Test Data` heading rather than
emitting an empty section.

## Pre-existing State sub-section

For matrix-driven TCs that need database state (duplicate, FK delete,
edit-non-existent, restore-after-soft-delete), the Test Data section
gets a `### Pre-existing State` sub-block before `### Form Input`. Each
entry is prose describing what the test setup needs:

```markdown
## Test Data

### Pre-existing State
- A Rule Template with Template Code "TC-DUP-001" already exists in the
  database (created via fixture or seed).
- The current user's Agent role has create permissions for Rule Templates.

### Form Input
* Template Code: TC-DUP-001 → duplicate('TC-DUP-001')
* Template Name: TC{tcNumber} Duplicate Test {timestamp}
* (...other fields with happy-path values...)
```

Pre-existing State stays prose-only at Phase 2. Phase 3 codegen emits
these as TODO comments in the spec's `afterEach` (or a `beforeEach`,
once the team's fixture pattern lands) for the developer to wire to
fixtures or seed scripts. The codegen does NOT auto-create database
state — see [`test-runner-cookbook.md → afterEach cleanup rules`](test-runner-cookbook.md#aftereach-cleanup-rules).

## Targeting rules per matrix-driven TC type

When a TC is generated by the Required Coverage Matrix (see
[`plan.md → Required Coverage Matrix`](plan.md#6-fs-validation-loop)),
pick one or more *target fields* to violate while keeping all other
fields at happy-path values.

| Matrix row | Target field selection | Other fields |
|---|---|---|
| Happy path | None violated | All happy-path |
| Required field missing | The specific required field named in the TC title | All others happy-path |
| Maximum length exceeded | The specific text field named in the TC title | All others happy-path |
| Duplicate value | The specific unique field named in the TC title; Pre-existing State names the duplicate value | All others happy-path |
| Invalid format | The specific typed field named in the TC title | All others happy-path |
| Cross-field comparison violation | Two fields involved in the comparison rule, set to violating values; TC title identifies the rule | All others happy-path |
| Whitespace-only | The specific required field named in the TC title (whitespace-only value) | All others happy-path |
| Authorization | None (all fields happy-path); Pre-existing State names the unauthorized user | All happy-path |
| Multi-tenancy isolation | None violated; Pre-existing State names the cross-tenant record | All happy-path |
| Concurrent edit | None violated; Pre-existing State names the stale-row scenario | All happy-path |

**One field violated per TC, by design.** The matrix produces one TC per
violation; one TC violates one rule. Multi-violation TCs (e.g. "max
length AND duplicate AT THE SAME TIME") are out of scope — they're not
testing one rule, and they make failure analysis ambiguous.

## When generation fails

Some fields will resist generation:

- The Entity / FRS captures the field but no constraints (no length, no
  format, no type beyond "string") — happy-path generation can produce
  something reasonable, but max-length / format-violation TCs can't be
  generated. Emit the TC with a TODO directive.
- The constraint is something the directive vocabulary doesn't cover
  (e.g. *"Field must be a comma-separated list of department codes"*) —
  emit the literal happy-path constraint as prose, no directive.
- The field is dynamic (`subject identifier` populated from another
  field's selection) — emit `(populated by step N)` as the value, no
  directive. Phase 3 codegen knows to skip the fill step.

A TODO Test Data entry looks like:

```
* Field Name: TODO — constraint not parseable; manual fill needed
```

Same honest-failure model as TODO selectors. Better than fabricating a
value the test would type and then fail on.

## Verification rules (ingest self-checks)

After populating Test Data for a TC, verify:

1. Every field referenced by a `fill` / `select` / `toggle` step has a
   Test Data entry — or the entry is explicitly marked TODO.
2. Every TC with a unique field has the field's happy-path value
   containing `{timestamp}` or `{uuid}`.
3. Matrix-driven TCs have exactly one field with a directive (one
   violation per TC).
4. Pre-existing State entries reference values that match the directive
   arguments (`duplicate('TC-DUP-001')` ↔ state describes a record with
   Code `TC-DUP-001`).
5. No two TCs in the same use-case sub-folder have the same happy-path
   values for unique fields without `{timestamp}` (would collide on
   parallel runs).

Failures block emission. Fix or flag with TODO before writing the file.

## Anti-Pattern: "The Hardcoded Test"

Skipping the templated value vocabulary and emitting literal values
("Template Name: My Test Template") for happy-path TCs on unique
fields, because the literal is shorter than the templated form and
"works locally". The cost: the second run of the same spec produces
a uniqueness-constraint violation against the row the first run
created (cleanup didn't fire, parallel-run isolation broke); the
suite goes red on a CI rerun and looks like a test failure when it
is actually a generation discipline failure; the operator chases a
ghost in the spec code rather than in this file. **Happy-path values
on unique fields MUST include `{timestamp}` or `{uuid}` — the
verification self-check fires on this and blocks emission.** TODO
literals are acceptable as honest gaps; hardcoded literals on unique
fields are not. Doctrinal anchor:
[`../PRINCIPLES.md`](../PRINCIPLES.md) — generation discipline,
verified at the point of emission, prevents drift that surfaces
hours or days later as opaque CI failure.
